# study–Flowlog 구현 계획 — 수업 연결과 버튼 추천
수정일: 2026-09-28. 최신 사용자 요청을 반영한 검토·설계이며 기능 구현은 아직 하지 않았다. 이전 계획의 메모 가져오기 및 독립적인 수업 시작 제안/자동 전환 단계를 대체한다.

## 1. 확정된 방향과 해석
- /study/는 로그인한 사용자 자신의 수업·공부·복습 기록, /study/learn/은 관리자 전용이다. 일반 사용자 연동은 learn에 의존하지 않는다.
- 사용자는 메모 복사가 아니라 수업 자체를 연결한다. 과목명/제목, 수업일, 일정, 메모, 공부·복습 상태를 관계를 통해 함께 조회한다.
- 초기에는 기타로 기록한 학교·이동을 사후 수업 입력 확인 과정에서 확인한다. 분류 추측만으로 원본 기록을 변경하지 않는다.
- 반복된 사용자 확인은 이후 해당 시간대의 버튼 추천 근거가 된다. 별도 수업 시작 팝업/알림 UI를 만들지 않고 기존 버튼 추천 UI를 확장한다.
- 메인 버튼은 최대 10개. 동의 횟수가 많아져도 버튼 자동 추가/교체, 타이머 자동 전환, 수업 자동 확정을 허가한 것으로 간주하지 않는다.
- 위치 기록은 앞선 범위를 유지하되 수업 연결 동의를 위치 수집 동의로 사용하지 않는다.

## 2. 소스에서 확인한 현재 상태
- MainButtonConfig.MAX_BUTTONS = 10.
- ButtonRecommendationEngine은 ETC의 제목·메모에서 학교→SCHOOL, 이동/통학/버스 등→MOVE를 추론한다. 90일 활동을 보고 점수 30 이상 또는 최근 14일 활동일 3일 이상이면 승격 후보가 된다. 이것은 현재 코드의 기준이며 이번 설계의 허용 횟수 기준이 아니다.
- 현재 추천 엔진은 해당 시간대와 수업 연결 허용 이력을 사용하지 않는다.
- ActivityViewModel.maybeGenerateMainButtonRecommendationMessage는 10개가 차면 반환한다. 수락 함수도 버튼 추가만 처리한다. 별도의 수동 replaceMainButton 기능은 존재한다.
- AiMessage.MainButtonRecommendation은 id/category/status만 가진다. 확인한 처리 경로의 메시지 상태는 메모리이고 거절 유예는 SharedPreferences다. 새 기능에는 기기 간 복원 가능한 판단 이력이 필요하다.
- 기존 EventLogEntity/Repository는 있지만 추천 노출·실제 반영·철회와 수업 연결의 의미를 표현하는 전용 계약이 없다. 기존 eventLogs는 관리자 조회 경로이므로 민감한 연결 맥락을 그대로 넣지 않는다.
- studyRecords는 done[3], note, skipped를 저장한다. 과목 제목·시간은 studyCourses, 수업 날짜는 courseId_date에서 파생된다. 공부/1차복습/2차복습 각각의 별도 제목·메모는 현재 없다.
- 따라서 수업 전체 연결은 단일 문서 복사로 구현할 수 없다. 과목+발생 수업+학습 단계 관계를 구성해야 한다.

## 3. 수업 연결의 의미
사용자 화면의 동작 이름은 '수업 연결'로 통일한다. 메모 가져오기/복사 버튼은 제거한다.

예: Flowlog 9월 29일 20:00–20:40 → 9월 28일 선형대수 수업의 1차 복습.
이 연결에는 과목, 원래 수업 날짜, 연결한 단계, 해당 단계의 예정일·완료일, 실제 Flowlog 시간이 함께 보인다. 복습 예정일을 수업일이나 실제 공부 시각으로 덮어쓰지 않는다.

연결 대상은 다음처럼 구분한다.
- COURSE_SESSION: 시간표의 수업 구간을 연결하는 맥락. 연결만으로 study의 공부 완료 체크나 출석을 변경하지 않는다.
- STUDY / REVIEW_1 / REVIEW_2: 해당 수업의 공부 또는 복습 단계.
같은 수업의 공부와 복습이 같은 날이어도 각각의 관계를 유지한다. 단계는 연결 선택 시 확정하며 완료 상태가 바뀌었다고 과거 연결 단계를 자동 변경하지 않는다.

표시와 역사 보존:
- 현재 제목·메모·전체 공부/복습 상태는 원본 참조로 조회한다. 원본 수정은 다음 동기화 후 상세 화면의 현재 정보에 반영한다. 웹은 원본 구독, Android는 캐시 갱신 시각과 함께 표시한다.
- 동시에 연결 당시의 최소 스냅샷과 sourceVersion/contentHash를 저장한다. 원본 수정 시 과거 시간 배분이나 확인 이력은 그대로 유지하고 당시 정보 보기로 제공한다.
- 원본 삭제/읽기 실패는 구분한다. 삭제된 원본은 스냅샷으로 표시하고 상태를 명시한다. 원본 삭제가 사본 삭제를 뜻하지는 않으므로 기록 전체 삭제에는 연결 스냅샷까지 삭제하는 경로를 제공한다.
- studyRecord가 아직 없어도 과목 일정으로 발생한 수업은 연결할 수 있다. 연결 때문에 study 완료 데이터를 임의 생성하지 않는다.
- 기존 메모는 수업 공통 메모다. 단계별 메모/제목이 필요해지면 study 원본 모델에 추가한다. 현재 존재하지 않는 데이터를 가져올 수 있다고 표시하지 않는다.

## 4. 사후 확인 흐름
1. 일과 이후 첫 실행 또는 사용자가 정리할 때 수업 자동 입력 후보를 제시한다. 정상적으로 연결 가능한 수업은 전체 선택 초안이다.
2. ETC 기록에 학교/이동 후보가 있으면 같은 화면에서 해당 기록이 무엇이었는지 확인한다. 제목만 학교로 보인다는 이유로 단정하지 않는다.
3. '이 기록은 학교였나요?'의 선택과 '선택한 수업을 연결할까요?'의 선택을 구분한다. 같은 저장 버튼으로 반영하더라도 결과는 별도로 기록한다. 사용자는 분류를 유지하고 연결만 할 수도 있다.
4. 학교로 확인하면 활동 category를 SCHOOL로 수정할 수 있지만 원래 누른 버튼 ETC와 변경 전 값/시각/근거를 보존한다. 메인 버튼 구성은 바뀌지 않는다.
5. 이동으로 확인하면 MOVE다. 통학과 시간표가 가까워도 학교 활동으로 바꾸거나 이동 시간을 수업 시간에 배분하지 않는다. 초기 자동 수업 연결 대상에서는 이동을 제외한다. 이동 중 공부는 사용자가 직접 선택한 별도 상세 구간으로만 처리한다.
6. 나중에/이번에는 아니요/이런 제안 그만 보기를 구분한다. 과목 체크 해제는 결석이나 추천 거절 전체로 해석하지 않는다.

학교 7시간에 수업 4시간을 연결해도 총시간은 7시간이다. 수업 단계별 시간은 그 안의 상세 배분이다. 일부 시간만 겹치면 그 부분을 제안하고, 겹치는 두 수업을 자동으로 이중 배분하지 않는다. 부모 활동의 시간 수정·삭제 시 연결도 재검토/삭제한다.

## 5. 기존 버튼 추천 UI의 확장
같은 카드에서 추천의 목적을 구분한다.
- 지금 사용: '이 시간에는 학교로 기록하는 경우가 많았어요' → 지금 학교로 기록. 메인 버튼 목록에 SCHOOL이 없어도 해당 분류로 시작할 수 있다. 현재 타이머가 있으면 기존 수동 전환 규칙을 따른다.
- 고정 버튼 구성: 자주 쓰는 학교를 메인에 두기. 10개 미만이면 명시적 추가, 10개면 사용자가 교체할 버튼을 선택하거나 구성을 유지한다.
- 이미 SCHOOL 버튼이 있으면 중복 추가를 제안하지 않고 현재 버튼 사용을 안내한다.
- 10개 상한은 설정 저장과 동기화에서도 검증한다. 카드의 일회성 활동 시작은 11번째 메인 슬롯을 만들지 않는다. 자동 교체나 새로운 상시 추천 줄은 만들지 않는다.

추천 근거:
- 학교 분류 확인, 수업/단계 연결 확인, 추천을 실제 사용한 결과는 서로 다른 신호다.
- 수학 과목 복습에 대한 동의를 학교 버튼 선호로 집계하지 않는다. MOVE 확인은 이동 추천 근거이고 SCHOOL의 허용 횟수에 합치지 않는다.
- 여러 날짜에 반복된 확인, 시간대/요일 일치, 실제 기록, 거절·철회·최근성, 현재 일정 예외를 조합한다.
- 초기 검증값으로 '최근 2~4주 내 서로 다른 3일 이상 명시적 학교 분류 확인'을 후보 자격에 사용할 수 있다. 이후 해당 시간대의 거절·철회와 충돌이 없을 때 추천한다. 이는 제안값이며 기존 엔진의 3일 기준을 검증 없이 복제하거나 최적값이라고 주장하지 않는다.
- 하루 수업 6개 일괄 연결을 허용 6회로 세지 않는다. 하나의 확인 작업과 서로 다른 날짜를 기준으로 계산한다.
- 노출되지 않은 추천에는 무응답을 집계하지 않는다. 추천 생성과 실제 화면 노출을 분리한다. 시간표만으로 생성한 기록이나 자동 초안은 독립적인 사용자 선호 증거가 아니다.
- 최신 거절/그만 보기/철회가 반영되며 반복 허용이 영구 동의가 되지 않는다. 추천은 기존 UI를 열거나 앱을 사용하는 때 표시하고 별도 수업 알림은 만들지 않는다.

## 6. 저장 구조 — 원본, 관계, 판단, 계산 결과
새 객체를 무조건 늘리는 대신 역할을 분리한다.

| 모델 | 저장 내용 | 기준 |
|---|---|---|
| 기존 studyCourses / studyRecords | 과목 정보·일정과 수업별 공부/복습 상태·메모 | study 정보의 원본 |
| 기존 activitySessions | 실제 시간, 확정 분류, 입력 출처/원래 버튼, 수정 버전 | 시간의 원본, 총시간은 여기서만 집계 |
| activityStudyLinks | activityId, courseId, lessonId, phase, segments, 수업일, 원본 참조, 연결 당시 snapshot/version, confirmedAt, revision, deletedAt | 수업 전체 연결과 시간 배분 |
| interactionDecisions | decisionId, 사용자, proposalId, 종류, 대상 ID, 이전/확정 값, 노출·응답·반영 시각, outcome, mutationId, supersedesDecisionId | 사용자가 무엇을 허용/거절/철회했고 실제 반영됐는지 |
| recommendationProfiles | 범주·요일·시간대별 확인/거절 요약, 근거 ID/계산 버전·기준 시각 | 원본 이력에서 재계산하는 캐시 |
| activityLocations(후속) | 시작/끝 좌표·측정 시각·정확도·수동 장소 | 별도 위치 동의 및 삭제 대상 |

activityStudyLinks의 유일 키는 hash(activityId, lessonId, phase). uid 경로/로컬 복합키로 계정도 격리한다. 같은 단계에서 여러 번 공부했으면 서로 다른 activityId로 연결한다. 한 활동 안의 같은 단계 여러 구간은 segments로 저장한다. 제목이나 변경 가능한 예정 시각은 키에 넣지 않는다. 기존 courseId_date는 유지하되 보강/날짜 이동을 지원할 때 원래 발생 ID를 보존하고 수정 날짜를 속성으로 둔다.

원본 참조는 허용된 같은 uid 아래의 경로만 구성한다. 임의 외부 경로나 다른 사용자 ID를 저장해 참조하지 않는다. snapshot에는 당시 제목·수업일·예정 시간·공통 메모·단계 및 완료 상태 등 회고에 필요한 값만 넣는다. 관계의 phase와 시간 배분은 원본 done[] 변경으로 재작성하지 않는다.

interactionDecisions는 모든 종류를 하나의 승인 카운트로 저장하지 않는다. 최소 종류:
- CLASSIFICATION_CONFIRM / STUDY_LINK_CONFIRM / STUDY_LINK_REMOVE
- BUTTON_USE / BUTTON_ADD / BUTTON_REPLACE
- RECOMMENDATION_SHOWN / RECOMMENDATION_DISMISS / RECOMMENDATION_SNOOZE / RECOMMENDATION_DISABLE
- UNDO(원래 decisionId 참조)
제안의 생성/실제 노출/응답/실제 반영 결과를 분리하고 실패·취소도 구분한다. confirmedCount 하나만 남기면 나중에 이유를 복원할 수 없다. 다만 위치나 메모 본문은 판단 로그에 중복 저장하지 않는다.

신규 관계·상세 결정·프로필·좌표는 users/{uid}/ 아래 소유자 전용 경로로 둔다. 기존 flowlog 재귀 허용 규칙 및 eventLogs 관리자 조회 규칙의 범위 밖으로 둔다. 기존 이벤트 저장의 구조를 참고하되 새 기록을 그대로 기존 공개 범위에 올리지 않는다. 활동 분류 자체는 기존 권한의 영향을 받는다는 점도 유지한다.

## 7. 실제로 기록이 남도록 하는 저장 규칙
- Room에는 관계와 결정 이력을 테이블로 저장하고 outbox에 넣는다. 화면 메시지 상태나 SharedPreferences만으로 동의를 보관하지 않는다.
- 웹과 앱 모두 동일한 mutationId/revision 계약을 쓴다. 분류 변경·수업 연결·확인 결과는 가능한 범위에서 한 트랜잭션으로 반영한다. 여러 작업이 필요하면 작업 상태를 저장해 재시도하고, 모두 완료되기 전 추천 학습 대상으로 삼지 않는다.
- 원격 버전이 달라지면 충돌을 알리고 이전 값을 무조건 덮어쓰지 않는다. 로컬 작업 시각과 서버 수신 시각은 분리한다.
- 동일 요청 재전송은 같은 mutationId로 중복 제거한다. 같은 화면 재렌더링을 새로운 노출·허용으로 세지 않는다.
- 취소/연결 삭제는 이전 결정을 참조하는 철회 이력으로 남기고 프로필을 재계산한다. 개인정보 전체 삭제 요청에는 역사 보존을 이유로 해당 이력을 남기지 않는다.
- 계정 전환 시 이전 사용자에게 속한 미전송 작업을 새 사용자로 업로드하지 않는다.
- 재설치·다른 기기에서도 관계와 유효한 선택 이력을 복원한다. 계산 캐시는 유실돼도 재구성 가능해야 한다.
- 기존 활동의 원격 수정을 Room에 반영하는 개선과 구버전 무버전 업로드 차단은 여전히 선행 조건이다.

## 9. AI 배정 계획

사용 가능한 company MCP 설정을 확인했다: Sol(gpt-6-sol, 접근 실패 시 설정된 gpt-5.6-sol fallback), Flash(gemini-3.8-flash-high), Opus(claude-opus-5-5). 표는 이 작업의 초기 배정이며 실제 실행 모델과 변경 사유를 실행 기록에 남긴다. 이번에는 담당만 정하며 작업자를 실행하지 않는다.

| 구현 단위 | 구현 담당 | 검토 담당 | 배정 근거 |
|---|---|---|---|
| 데이터 계약·Room 마이그레이션·Firestore 권한 | Sol | Opus | 여러 저장 계층을 일치시켜야 하므로 구현을 한 담당이 묶고, 다른 모델이 소유권·원본/사본·삭제 불변조건을 검사 |
| 웹–Android 수정·충돌·삭제·outbox 동기화 | Sol | Opus | 활동·관계·결정의 커밋 경계와 재시도 처리를 같은 맥락에서 구현하고 실패 순서별 독립 검토 |
| 수업/공부/복습 연결·해제·현재 원본/당시 정보 조회 | Sol | Flash | 저장 계약 담당이 관계 로직을 구현하고, 기존 소스 대조 검토를 완료한 Flash가 날짜·단계·중복 집계를 확인 |
| 웹 블록 상세 및 일과 후 수업 선택 화면 | Flash | Sol | 확정된 데이터 계약 위의 UI로 범위를 한정하고 구현 담당과 다른 모델이 저장 연결·오류·중복 제출을 검토 |

| 위치 시작/끝 기록(후속 단계) | Sol | Opus | Android 권한·지연 콜백·활동 식별자 변경을 묶고 위치 실패 및 계정 전환/삭제 시나리오를 검토 |

Codex는 실제 소스 수집, 계약 확정, 파일 반영, 테스트 실행, 통합 및 최종 결과 대조를 맡는다. company 작업자는 도구 없는 문맥 입력/결과 출력 방식이므로 직접 저장소를 수정하거나 테스트를 실행했다고 간주하지 않는다. 최신 통합본과 실제 테스트 증거를 위 검토자에게 전달해 승인받는다.

평가 근거의 한계: company의 Sol 구현 평가에는 긍정 사례가 있지만 표본이 적고 실제 모델 식별이 미보고된 사례가 있다. Flash는 이번 수정 계획 검토를 완료했지만 일반 구현·테스트 평가에는 수정 필요 사례도 있다. Opus는 이번 분석에서 /study/learn 관리자 범위를 추천 기능과 혼동했으므로, 자유로운 요구사항 재해석 대신 명시적인 불변조건과 원본 소스로 검토 범위를 제한한다. 모델 이름만으로 품질을 보장하지 않는다.

진행은 저장 계약 → 동기화 → 연결 로직 순서다. 계약이 확정된 뒤 웹 UI(Flash)와 Android UI(Sol), 테스트(Flash)를 파일 범위를 분리해 병행할 수 있다. 같은 ActivityViewModel이나 스키마 파일을 두 담당이 동시에 고치지 않는다. Sol/Opus는 현재 각각 동시 1회 제약이 있으므로 해당 작업을 직렬 배치한다. 일시 장애는 같은 요청 예산 안에서 재시도하며 지속 실패나 결과 품질 문제로 담당을 바꾸면 사유와 실제 모델을 알린다.
