# study–Flowlog 기록 상세화 검토
검토일: 2026-09-28. 로컬 소스 기준. 운영 사이트는 웹 조회 도구에서 열리지 않아 배포본과 로그인 후 실제 데이터는 검증하지 않았다. 아래 건수는 실제 보유량이 아닌 가정이다. 앱 기능 변경·배포는 하지 않았다.

추천은 **2안과 블록 상세 편집을 먼저 묶고, 위치를 추가한 뒤, 1안을 선택 기능으로 제공**하는 순서다. 타이머는 시간의 기준, study는 그 시간에 대한 과목·내용의 근거로 사용한다.

## 현재 구조에서 확인한 사실
- studyCourses: 과목명, 학기 시작·종료일, 요일, 시작·종료 시각. studyRecords: courseId_날짜를 키로 공부·1차복습·2차복습 완료일, 메모, 건너뜀. 완료 체크는 출석 증명이나 실제 공부한 분 수가 아니다.
- Flowlog ActivitySession: 시작·끝·소요시간, 제목, 분류, 메모, 태그, sourceType/sourceId 등. 구조화된 수업 상세와 위치 필드는 추가 설계가 필요하다.
- 오늘의 흐름 블록은 현재 시간·제목 툴팁이다. 예측 블록도 함께 그리므로 실제 기록과 구분해야 한다.
- StudyPlanAutoStartReceiver는 이미 있지만 organizedPetites 기반이며 실행 중인 타이머를 변경하지 않는다. 별도 studyCourses를 곧바로 읽는 완성된 연동으로 볼 수 없다. 기존 STUDY_PLAN 데이터 정리 코드도 있어 연결 경로 재검증이 필요하다.
- Android restoreActivities는 같은 activityId가 있으면 건너뛴다. 업로드는 merge이지만 같은 필드의 오래된 값은 덮어쓸 수 있다. 웹 편집에 앞서 기존 행 갱신·충돌 처리·삭제 전파를 보완해야 한다.
- 현재 Manifest에는 위치 권한이 없다.

## 두 안의 비교
| 방식 | 장점 | 핵심 문제 | 권장 역할 |
|---|---|---|---|
| 1안: 정시에 학교/수업으로 전환 | 입력 부담이 가장 적고 수업별 경계가 생김 | 휴강·결석·지각·이동 중인 상황에도 계획이 사실처럼 기록될 수 있음. 알람 지연·오프라인 일정 변경도 처리 필요 | 사용자가 켜는 보조 기능 |
| 2안: 일과 뒤 과목 선택 | 기존 실제 시간 유지, 과목 제외·수정 쉬움 | 기본 전체 선택을 무심코 저장하면 부정확한 정보가 쌓일 수 있음 | 우선 구현 |
| 블록 상세 편집 | 잘못된 기록을 언제든 정정하고 내용을 보강 | 웹–앱 동기화와 원본 식별이 선행돼야 함 | 공통 기반 |
| 이동 시작·끝 위치 | 이동에 출발지·도착지 맥락 추가 | 권한 거절, 실내 오차, 누락된 끝점, 민감정보 노출 | 다음 단계 |

2안의 화면은 마지막 예정 수업 종료 뒤, 또는 이후 첫 앱 실행 때 한 번 제안한다. 연결 가능한 수업은 기본 전체 선택하고 한 과목씩 해제할 수 있게 한다. 이미 반영한 항목은 중복 선택을 막고, 건너뜀 표시와 시간 충돌은 별도 확인 대상으로 보여준다. 매번 방해하지 않도록 나중에·오늘 숨기기도 제공한다. 시간이 됐다는 이유로 저장하지 않고 [선택한 수업 연결]을 눌러 확정한다. 체크 해제는 '연결하지 않음'이며 결석으로 추론하지 않는다.

예: 학교 09:00–16:00(7시간)에 수학 09:00–10:00, 영어 10:00–11:00을 연결하면 총시간은 계속 7시간이다. 과목별 2시간은 그 안의 상세 배분이고 남은 5시간은 미분류다. 영어를 해제해도 학교 7시간 자체를 줄이지 않는다. 예정 시각으로 배분한 경우 '시간표 기준'을 표시한다. 겹치는 과목은 자동으로 둘 다 합산하지 않는다.

학교 기록이 09:30에 시작했다면 09:00 수업의 기본 배분은 겹치는 09:30–10:00만 제안하고 사용자 확인을 받는다. 기존 기록이 전혀 없으면 연결할 대상이 없다고 표시한다. 새 기록 생성은 별도 행동이며 예정 기반·사용자 확인 출처를 남긴다.

1안은 초기에는 [수업 시작] 제안이 적합하다. 완전 자동을 켜는 경우 기존 타이머 종료와 새 타이머 시작을 한 전환으로 처리하고 중복 알람·다중 기기 실행을 막는다. 수동 전환을 우선하고 실행 취소를 제공한다. 학교는 상위 분류, 과목은 상세로 두면 버튼이 과목 수만큼 늘지 않는다. 자동 기록과 사용자가 확인한 기록을 분리해 통계에 표시한다.

## 블록을 눌렀을 때
상세 패널에 시간·분류·제목·메모, 연결 과목과 공부 내용, 출발지·도착지, 출처·확인 상태를 보여준다. [수정] [study에서 가져오기] [수업 연결]을 제공한다. 시간 변경은 별도 저장 전 미리보기로 총시간과 겹침 변화를 확인한다.
- 날짜와 시간대가 맞는 study 수업을 먼저 추천하되 직접 다른 날짜·수업을 고를 수 있게 한다.
- 원본 메모 미리보기 후 추가/교체를 선택한다. Flowlog 메모를 조용히 덮어쓰지 않는다.
- 실제 활동 ID를 렌더링 데이터까지 유지한다. 묶음 표시가 여러 기록에 대응하면 먼저 원본 기록을 선택한다. 예측 블록은 '기록으로 만들기'를 거쳐야 편집 가능한 실제 활동이 된다.
- lessonId와 가져온 내용의 스냅샷·가져온 시각/버전을 함께 보관한다. study의 원본 수정·삭제로 과거 회고를 조용히 바꾸지 않는다. 초기 연동은 study→Flowlog 가져오기로 제한하고 study 완료 체크를 역으로 변경하지 않는 설계를 권장한다.

구현상 ActivityDetail에 activityId, lessonId, 범위, 메모 스냅샷, source, confirmationStatus, revision을 두는 방안을 권장한다. 한 활동에 여러 수업, 한 수업에 여러 활동을 연결할 수 있어야 한다. activityId+lessonId 등 안정적인 키로 재시도 중복을 방지한다. 총시간은 부모 기록을 한 번만 집계하고 상세 시간을 더하지 않는다. 타임존은 Asia/Seoul을 명시하고 날짜 경계·휴강·보강·시간표 변경 버전을 처리한다.

## 위치 수집
이동 버튼을 누르면 즉시 타이머를 시작하고, 화면이 열린 상태에서 현재 위치를 비동기로 한 번 요청한다. 이동 종료 또는 다음 활동 전환 시 화면이 열린 경우 끝 위치를 한 번 요청한다. 시작/종료 시각은 위치 응답을 기다리지 않는다. 위젯·알림·자동 전환처럼 앱이 보이지 않는 경로의 위치 접근은 별도 검증 대상으로 두고, 초기 버전은 누락 상태로 남긴 뒤 상세 화면에서 보완한다.
- 위도·경도뿐 아니라 측정 시각, 정확도(m), 획득 상태를 저장한다. 늦게 도착한 응답은 해당 이동 ID에 연결한다.
- 권한 거절·시간 초과·오프라인에도 시간 기록은 성공해야 한다. 앱의 위치 획득은 GPS뿐 아니라 기기 위치 제공자를 사용하며 실제 정확도는 보장할 수 없다.
- 오래된 마지막 위치를 현재 위치로 쓰지 않는다. Android 공식 문서는 현재 위치 요청 getCurrentLocation을 안내한다. [Android 위치 획득](https://developer.android.com/develop/sensors-and-location/location/retrieve-current), [위치 권한](https://developer.android.com/develop/sensors-and-location/location/permissions).
- 상세 화면에서 '집→학교', 건물명, 이동 수단을 직접 보완한다. 과거 기록을 편집하면서 지금 위치를 과거 도착지로 자동 저장하지 않는다.
- 두 점으로 출발·도착과 기록된 이동 시간을 알 수 있지만 실제 경로·주행거리·이동수단·실제 도착시각은 확정할 수 없다. 종료 버튼 시각과 도착시각도 다를 수 있다.

정밀 좌표와 study 상세 메모는 소유자 전용 별도 문서/컬렉션에 저장하는 방안을 권장한다. 현재 activitySessions는 관리자도 읽을 수 있고 studyRecords는 소유자만 읽을 수 있어, 메모를 복사하는 것만으로 접근 범위가 확대될 수 있다. 내보내기·AI 전달은 기본 제외, 공유 시 장소 별칭만 선택적으로 포함하도록 한다. 원시 좌표 보존 기간·삭제·백업 및 파생 장소 삭제를 구현 전에 정한다.

## 개인화 정보는 얼마나 쌓이나
예시 가정: 주 5일 × 하루 수업 4개 × 4주 = 수업 후보 80개, 이동 하루 2회 × 주 5일 × 4주 = 이동 40개·위치 최대 80점. 메모 하루 1개 × 주 5일 × 4주 = 최대 20개. 사용자 확인률·위치 성공률이 낮으면 유효 건수는 줄어든다. 이 수치는 서로 독립인 학습 표본 수나 현재 보유량이 아니다.

| 데이터 | 얻을 수 있는 개인화 | 한계 |
|---|---|---|
| 과목·연결 시간 | 과목별 시간 분포, 반복되는 시간대 | 시간표 배분은 실측과 구분 |
| 공부·복습 완료일 | 수업 이후 복습 간격·지연 | 이해도·성적·집중력은 알 수 없음 |
| 내용·태그·메모 | 어떤 단원/주제를 언제 다뤘는지 검색·회고 | 메모 작성 편향, 텍스트에 민감정보 포함 가능 |
| 이동 끝점·시간 | 반복 출발/도착 쌍의 기록 시간 요약 | 경로·수단·실제 도착시각은 불명 |
| 수정·제외 이력 | 어떤 제안이 자주 틀리는지 평가 | 체크 해제만으로 결석·선호를 단정 금지 |

2–4주면 개인별 요약과 반복 후보를 제시해 볼 수 있다. 이는 정확도를 보장하는 최소 기간이 아니다. 8–12주가 되어도 과목·요일·장소로 나누면 표본이 작고 시험 기간 등으로 달라질 수 있다. '최적 학습 시간'이나 '생산성을 높이는 장소'는 이 정보만으로 확정하지 않는다. 장소별 학습시간 비교도 실제 학습 기록에 장소가 연결된 경우에만 가능하다.

수집량보다 확인된 연결 비율, 추정시간 비율, 장소 측정 성공률·신선도, 자동 제안 수정률, 중복·겹침 비율을 함께 측정하는 편이 유용하다. 사용자가 입력한 계획으로 만든 기록을 다시 근거 삼아 추천하는 순환도 방지해야 한다.

## 구현 순서와 검증
1. 활동 ID 유지, 상세 저장소·권한, 버전 기반 웹–Room 충돌 처리 및 삭제 전파.
2. 블록 상세 편집 + 2안의 선택 연결 + study 메모 가져오기.
3. Android에서 사용자 동작 시 이동 양 끝점 획득.
4. 자동 제안의 수정률을 확인한 뒤 1안의 선택적 자동 전환.

필수 검증: 같은 수업 두 번 가져오기에도 총시간 불변, 부분 겹침/휴강/보강, 웹과 오프라인 앱 동시 수정, 부모 삭제 후 상세 정리, 예측 블록 편집 방지, 위치 거절/지연/시작만 성공, 알람 지연/재부팅/수동 전환 우선. 이번 검토에서는 소스만 읽었으며 실행 테스트와 실제 개인정보 건수 조회는 하지 않았다.
